## ADR-001：采用纯前端 + 第三方 CORS 代理架构，不建自有后端

- **日期**：2026-10-11（提交 `e5cb7fb`）
- **状态**：已采纳
- **背景（遇到了什么问题）**：
  浏览器直接 `fetch` B 站 API（`api.bilibili.com/x/vas/...`）会被 CORS 策略拦截 —— B 站 API 不为任意来源返回 `Access-Control-Allow-Origin`。要在纯静态页面里拿到 JSON 数据，必须绕过这道限制。同时项目希望零运维成本，能直接挂 GitHub Pages。

- **考虑过的方案**：
  1. **自建后端 / Serverless 代理**：Node 服务转发请求，可控性最高。
  2. **浏览器扩展**：扩展有更高网络权限，可绕过 CORS。
  3. **纯前端 + 第三方公共 CORS 代理**：用一个既有的转发服务代理 API 请求。
  4. **油猴脚本 / 用户侧本地服务**：注入到 B 站页面，同源请求。

- **决策**：采用方案 3。API 请求统一经 `https://p.xrl.im/?url=<encodeURIComponent(apiUrl)>` 转发；图片本体**不走代理**，由浏览器直连 B 站 CDN。

- **为什么选这个**：
  - 零运维、零部署成本，`pnpm build` 出来的 `dist/` 直接推 GitHub Pages，CI 只做构建不做后端。
  - B 站 CDN 自身返回 `Access-Control-Allow-Origin: *`，图片资源根本不需要代理；配合 `index.html` 的 `<meta name="referrer" content="no-referrer">` 让请求不带 `Referer`，同时解决防盗链。代理只用在「必须绕 CORS 的 JSON 接口」上，面最小。
  - 全部图像加工在浏览器 Canvas 里完成，不需要服务端算力。

- **为什么不选其他**：
  - 方案 1 引入服务器成本、部署复杂度与一个需要长期维护的运行时，与「工具型小站」的定位不匹配。
  - 方案 2 / 4 要求用户安装扩展或脚本，门槛远高于「打开网页粘贴链接」，且分发渠道受限。

- **后果**：
  - ✅ 部署链路极简：push main → GitHub Actions 构建 → GitHub Pages，无后端可宕。
  - ✅ 全部加工在本地浏览器完成，用户素材不经过自有服务器。
  - ⚠️ **`p.xrl.im` 是单点故障**：该代理不可用则解析功能整体失效，项目无法自愈。已在 README「已知限制」中明示。
  - ⚠️ 依赖 B 站 CDN 的 CORS 放行策略；策略收紧则图片抓取与切割失效。
  - ⚠️ 代理是第三方服务，隐私与稳定性均不受本项目控制（虽只转发公开 API 的 URL）。

- **何时重新审视**：`p.xrl.im` 出现不可用 / 限流 / 停服时；或 B 站 CDN 收紧 CORS 策略导致图片无法直连时。届时优先考虑加一层可切换的多代理回退，或退而自建轻量 Serverless 代理。

## ADR-002：UI 采用 `@m3e/react`（Material Design 3 Expressive）而非通用组件库

- **日期**：2026-10-11（提交 `e5cb7fb`）
- **状态**：已采纳
- **背景**：需要一个具备完整 Material 3 设计令牌、深浅色主题、且移动端触摸友好的组件库，避免自己手写 dialog / card / button / snackbar / progress。

- **考虑过的方案**：
  1. Material Web（`@material/web`，M3 但非 Expressive）。
  2. `@m3e/react` + `@m3e/web`（M3 Expressive，Lit Web Components + React 绑定）。
  3. MUI / Chakra 等主流 React 组件库（非严格 M3）。
  4. 全手写 CSS 组件。

- **决策**：采用方案 2。组件从 `@m3e/react/*` 子路径按需导入；主题由 `M3eTheme` 统一注入。

- **为什么选这个**：项目遵循 Material 3 Expressive 设计语言（仓库配套有 `material-3` skill），`@m3e/react` 是其中真正支持 Expressive 的实现，设计令牌（`--md-sys-color-*`）齐备、深浅色开箱即用。

- **为什么不选其他**：MUI / Chakra 不是严格的 M3 令牌体系，混用会与设计语言冲突；全手写要重造 dialog 焦点管理、snackbar 时序等大量细节。

- **后果**：
  - ✅ 令牌体系完整，主题切换（含 Canvas 预览读令牌）一致。
  - ⚠️ **上游缺口需自行补齐**：`@m3e/react` 的 snackbar 入口只 re-export Lit 元素类，未提供 React 绑定，故用 `@lit/react` 的 `createComponent` 在 `src/lib/m3eSnackbar.ts` 手工封装（映射 `toggle` → `onToggle`）。
  - ⚠️ **组件有非直觉陷阱**，已在 ARCHITECTURE「重要技术边界 7」记录：`m3e-card` 图片必须作 `slot="header"` 直接子元素；关闭态 `m3e-dialog` 仍 `display:flex`，需 CSS 移出布局。
  - ⚠️ 令牌读取有边界：只能用 `--md-sys-color-*` / `--md-sys-shape-*`；`--m3e-*` 仅作组件 cssprop，写进普通 CSS 不生效（历史上误用导致深色模式黑字陷深底，后修正）。

- **何时重新审视**：上游补齐 snackbar 等 React 绑定后可移除本地封装；或 `@m3e` 出现破坏性变更、停止维护时。

## ADR-003：链接类型自动判定（`lottery_id` 有无），而非让用户选择

- **日期**：2026-10-12（提交 `7b8d46e`）
- **状态**：已采纳
- **背景**：新增个性装扮支持后，两类链接（数字周边活动 / 装扮详情）都含 `?id=...`，长得极像，但走完全不同的 API（`dlc_act/lottery/...` vs `garb/v2/mall/suit/detail`）。需要决定「谁来区分这两类」。

- **考虑过的方案**：
  1. UI 上加一个「链接类型」选择器让用户手动指定。
  2. 从链接的路径 / host 特征区分（`blackboard/activity-` vs `h5/mall/suit`）。
  3. 从查询参数特征区分：含显式 `lottery_id` → 数字周边；否则 → 装扮。

- **决策**：采用方案 3。`parseUrl` 返回可辨识联合 `ParsedUrl`：取 `id`（回退 `act_id`），有 `lottery_id` 判为 `{kind:'dlc', id, lottery_id}`，否则判为 `{kind:'garb', itemId}`。

- **为什么选这个**：
  - `lottery_id` 是数字周边活动的**本质特征**（抽奖型活动才有），比路径匹配更稳定 —— B 站页面路径可能变，但「有抽奖 ID 才是 DLC 活动」这个语义不变。
  - 用户零操作：不需要理解两类链接的区别，粘贴即可。
  - 可辨识联合让下游 `useDlcData` 的 `switch(kind)` 分派有类型安全，且空态文案能按 kind 区分（「活动暂无数字周边」vs「装扮已下架」）。

- **为什么不选其他**：
  - 方案 1 把机器能判定的事推给用户，增加误操作与学习成本。
  - 方案 2 路径匹配脆弱，B 站改版即失效；且同一活动可能有多个入口路径。

- **后果**：
  - ✅ 单输入框即可处理两类链接，`ImageGallery` 得以做成「通用分区渲染」（不感知数据来源，DLC 与装扮共用）。
  - ✅ e2e 专门覆盖了「无 `lottery_id` 不误判为格式错误」这一回归点。
  - ⚠️ 判定依赖 `lottery_id` 语义稳定；若 B 站未来给装扮也加 `lottery_id`，判定会失效。
  - ⚠️ 装扮链接的 `id` 被直接当作 `item_id`，假设了两者的等价关系。

- **何时重新审视**：出现第三类链接，或 B 站改变了 `lottery_id` / 装扮 `id` 的语义时。

## ADR-004：网格推断做成「零 DOM 依赖的纯计算模块」，与实际切割分离

- **日期**：2026-10-11（提交 `e5cb7fb`），后续多次迭代
- **状态**：已采纳
- **背景**：表情切割需要一套复杂的像素分析算法（内容带分段、间隙中点拟合周期、接缝颜色剖面兜底）。这些逻辑既要在浏览器里跑，也需要能离线诊断、独立验证。

- **考虑过的方案**：
  1. 把推断逻辑直接写进 `EmojiCropDialog` 组件。
  2. 推断与切割都放一个 `imageProcessing.ts`，允许自由使用 canvas。
  3. 拆成两层：`gridAnalysis.ts` 纯计算（只吃 `Uint8ClampedArray` + 宽高，只吐参数与矩形），`imageProcessing.ts` 负责 DOM / canvas 像素提取与编码。

- **决策**：采用方案 3。`gridAnalysis.ts` 不 import 任何依赖 DOM 的东西；像素提取（`getImageData`）全在 `imageProcessing.ts` 完成后传入。`gridCellRects` 作为预览与切割共用的**唯一几何来源**。

- **为什么选这个**：
  - 纯函数可在 Node 中直接跑单测、可在 `scripts/diagnose-crop.mjs` 里离线诊断，不必启动浏览器。
  - 几何单点化杜绝「预览一套格子、切割另一套格子」的偏差 —— 这是所见即所得的前提。
  - 算法迭代（推断策略调过很多版）不牵动 UI 与编码逻辑，边界清晰。

- **为什么不选其他**：方案 1 把算法焊死在组件里，无法独立测试；方案 2 让 DOM 依赖渗透进算法层，丧失离线诊断能力。

- **后果**：
  - ✅ 算法可测、可诊断、可独立演进；`gridCellRects` 单点保证预览即产物。
  - ⚠️ 需要维护 `alphas[0]` 是「主 alpha（静态图 alpha / 动图全帧联合 alpha）」这一约定，`loadEmojiSheet` 建立、`inferGridParams` 依赖，改一处必须同步。
  - ⚠️ 纯计算与 DOM 层的边界需要纪律维持（AGENTS.md 已列为硬规则）。

- **何时重新审视**：推断算法稳定后不再频繁改动即可长期保持；若引入 Web Worker 做重型像素计算，需重新评估数据传递边界。

## ADR-005：网格参数「推断只求接近，精确对齐交给人」

- **日期**：2026-10-12（提交 `353db25`，切割改为参数预览 dialog）
- **状态**：已采纳
- **背景**：早期版本尝试让 `inferGridParams` 直接给出「精确到像素」的切割结果，全自动、无 dialog。但真实表情排版千变万化 —— 贴纸紧贴、跨格宽构图、动画道具越界、满幅零间隙、行内大面积粘连 —— 没有任何启发式能保证对所有排版都 100% 精确。追求全自动导致代码里堆满脆弱的 corner-case 补丁。

- **考虑过的方案**：
  1. 继续追求全自动精确推断，不断加特例。
  2. 让用户完全手动框选切割区域（自由裁剪）。
  3. 推断给「接近的初始值」，在预览 dialog 里暴露全部 8 个参数供用户微调，人做最终决定。

- **决策**：采用方案 3。切割从「一键下载」改为「参数预览 dialog」：`inferGridParams` 填初始值 → `drawPreview` 画红蒙层 + 白描边 → 用户改 `ParamStepper` → `gridParamsValid` 校验 → 确认才下载。dialog 首开后保持挂载，重开保留微调（支持迭代式工作流）。

- **为什么选这个**：
  - 把不可靠的「推断」降级为「初始值建议」，最终正确性由人保证 —— 而人看一眼红蒙层就能判断切得对不对，成本极低。
  - 释放算法压力：`gridAnalysis` 可以用大胆启发式而不必穷尽 corner case（ARCHITECTURE「技术边界 3」）。
  - 8 参数全暴露 + 实时预览，任何推断失准都能被手动纠正，不存在「切坏了还没救」的情况。

- **为什么不选其他**：
  - 方案 1 是无底洞，每个新排版都要加特例，且特例之间会互相打架。
  - 方案 2 把负担全推给用户，丧失自动推断的价值，且自由裁剪对均匀网格是杀鸡用牛刀。

- **后果**：
  - ✅ 算法边界清晰，可维护性大幅提升；用户始终有兜底手段。
  - ✅ e2e 覆盖了 dialog 全流程：8 参数齐全、红蒙层像素存在、背景 / ESC 不关、取消不下载、重开保留微调、改行数切出对应格数、非方窗如实取消「1:1」标注。
  - ⚠️ 多一步用户交互（不再是纯一键）；但换来了正确性保证。
  - ⚠️ 依赖预览的直观性 —— 红蒙层挖空做法保证「格子边缘半像素也不被误标」。

- **何时重新审视**：若未来推断精度足够高、且用户反馈微调步骤多余，可考虑加一个「信任推断，一键切割」的快捷路径，但**不应移除** dialog。

## ADR-006：动图逐格重编码，动格出 GIF、静格出 PNG

- **日期**：2026-10-11（提交 `e5cb7fb`）
- **状态**：已采纳
- **背景**：动态表情包是一张动画拼图（GIF / 动画 WebP / APNG）。用户需要的是切好的**单个动图**，而非静止首帧。同一张拼图里有的格在动、有的格是静止的。

- **考虑过的方案**：
  1. 只解首帧，全部输出静态 PNG（放弃动画）。
  2. 逐帧解码，每格都重编码为 GIF（无论动静）。
  3. 逐帧解码，每格独立判断：有效帧 >1 输出动画 GIF，否则输出 PNG。

- **决策**：采用方案 3。用 WebCodecs `ImageDecoder` 解出全部已合成帧（`decodeAnimatedFrames`），逐格用**同一裁剪几何**绘制到 1:1 方画布，去除与前一帧完全相同的帧（`imageDataEqual`，时长并入前帧），有效帧 ≤1 输出 PNG，否则 `encodeCellGif` 逐帧量化编码。

- **为什么选这个**：
  - 保留动画是动态表情包的核心价值，方案 1 不可接受。
  - 静止格编成 GIF 是浪费（体积大、无收益），方案 3 按需选择格式。
  - 帧间帧内用同一几何裁剪，保证动画对齐；去重合并时长避免冗余帧。

- **为什么不选其他**：方案 1 丢动画；方案 2 对静止格产出臃肿 GIF。

- **后果**：
  - ✅ 动静混排的拼图各得其所；GIF 保留每帧时长与透明。
  - ⚠️ **依赖 WebCodecs `ImageDecoder`**：不支持的环境（旧 Safari 等）静默退回首帧路径，动画包退化为静态切割，不报错但丢动画。已在 README「已知限制」明示。
  - ⚠️ GIF 仅 1-bit 透明，需按 `cutoff=128` 二值化 alpha，半透明边缘会被压平。
  - ⚠️ 逐格逐帧 canvas 绘制 + 量化编码，大图较慢（e2e 单测超时设 120s）。

- **何时重新审视**：需要更高保真（保留半透明边缘）时考虑输出 APNG / WebP；`ImageDecoder` 覆盖率成为主要瓶颈时考虑引入 JS 解码兜底（如 `gif.js` 解码路径）。

## ADR-007：e2e 一律打真实 B 站接口，不 mock

- **日期**：2026-10-11（提交 `e5cb7fb`）起，后续持续
- **状态**：已采纳
- **背景**：项目验收标准是「高覆盖率 E2E」。需要决定测试是对真实 B 站数据跑，还是对 mock 数据跑。

- **考虑过的方案**：
  1. Mock B 站 API 响应，用固定 fixture 测试。
  2. 打真实接口、真实活动链接，对下载产物做字节级断言。
  3. 两者结合：核心算法用 fixture 单测，链路用真实接口 e2e。

- **决策**：采用方案 2。`e2e/gallery.spec.ts` 的 16 个用例全部打真实活动链接（`id=104978`、`114461`、`105575`、`111546`、`107081`、`112538` 等），断言打在产物字节上（ZIP 条目数、PNG/GIF 魔数、`w===h`、GIF 帧数与每帧时长、透明标记）。

- **为什么选这个**：
  - 网格推断算法的价值恰恰在于处理**真实世界千奇百怪的排版**；mock 数据只会覆盖自己想得到的 case，测不出真实失准。
  - 真实活动链接天然提供了 diverse 的 fixture：紧贴型、粘连型、跨格宽、动画越界、竖版、满幅零间隙 —— 每个用例对应一类真实排版回归。
  - 产物字节级断言比截图 / DOM 文本更硬，能抓住「切出来数量对但尺寸错了」「GIF 丢了透明」这类真实缺陷。

- **为什么不选其他**：方案 1 的 mock 会让算法在假数据上「看起来对」，丧失回归价值；方案 3 值得未来补充（算法层单测），但当前真实 e2e 已覆盖核心链路。

- **后果**：
  - ✅ 测试覆盖真实排版，回归价值高；`id=112538` 等用例锁住了具体的推断精度回归（边距 56/40、格 200×200）。
  - ⚠️ **e2e fixture 会腐烂**：活动下线、素材变更、B 站改版都会导致用例失败，且失败原因在测试之外。已在 README「已知限制」明示。
  - ⚠️ 依赖网络与 `p.xrl.im` 代理可用；测试慢（120s 超时、串行、`msedge` channel）。
  - ⚠️ 无法在完全离线 / CI 隔离网络环境稳定运行。

- **何时重新审视**：活动链接大面积失效导致 e2e 无法维护时，考虑为核心算法补充离线 fixture 单测（方案 3），把「算法正确性」与「真实数据可用性」两类回归分离。

## ADR-008：产物与测试材料不入库，CI 构建部署 GitHub Pages

- **日期**：2026-10-11（提交 `e5cb7fb`）起
- **状态**：已采纳
- **背景**：需要确定构建产物、测试产物的版本控制策略，以及部署方式。

- **决策**：
  - `dist/`、`e2e-artifacts/`、`test-results/`、`node_modules/`、`playwright-report/` 全部 `.gitignore`，不入库（当前均未被 git 跟踪）。
  - 部署走 GitHub Actions：push `main` → `pnpm install --frozen-lockfile` → `pnpm build` → `actions/deploy-pages`。`concurrency: pages` + `cancel-in-progress` 防并发部署。
  - Vite `base: '/bilibili-dlc-getter/'` 固定为仓库名（GitHub Pages 项目站点的子路径要求）。

- **为什么选这个**：产物是可重建的派生物，入库只会制造无意义的 diff 与仓库膨胀；CI 构建保证线上产物与 `main` 源码严格一致。

- **后果**：
  - ✅ 仓库干净；部署全自动，push 即上线。
  - ⚠️ `base` 与仓库名强耦合，改仓库名必须同步改 `vite.config.ts`。
  - ⚠️ `e2e-artifacts/` 不入库意味着切割产物的截图 / 切片只作本地人工核验材料，CI 不保留（若需要产物留档需另配 artifact 上传）。

- **何时重新审视**：需要在 CI 中留存 e2e 产物做视觉回归时；或迁移到自定义域名（`base` 需改回 `/`）时。
